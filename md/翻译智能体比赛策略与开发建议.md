# 翻译智能体比赛策略与开发建议

> 基于 LinguaGraph 现状评估 | 2026年5月 | 距比赛约5-6周

---

## 一、差异化定位：从"翻译工具"升级为"小语种学习教练"

当前 LinguaGraph 是一个中规中矩的翻译批改工具。要在比赛中脱颖而出，需要回答评委一个问题：

> "市面上翻译工具有几百个，你这个 Agent 到底做了什么其他工具做不到的事？"

项目已有三个差异化基因，但尚未充分利用：

| 基因 | 现状 | 建议强化方向 |
|---|---|---|
| 小语种 | 只做了中俄，和通用翻译没区别 | 打"资源匮乏语言"这张牌——展示 Agent 在缺少语料时如何工作 |
| 学习闭环 | 设计文档写得很完整 | 把闭环做成**可演示的**，而不是 PPT 上的概念 |
| Multi-Agent | 其实是单链路 pipeline | 引入**多 Agent 协作与辩论**，这是比赛加分项 |

---

## 二、5-6 周内最值得做的 5 件事（按优先级）

### 第 1 优先：把 LLM 真正用起来

当前代码最大的问题是 **LLM 被架空**：

- 练习生成调了 LLM 但最后用的是硬编码题库（`nodes.py:116`，`_pick_exercise` 覆盖了 LLM 输出）
- 评分主要靠正则规则（`learning.py:196-204`）
- 结果：Agent 对任何新语种、新领域、新题目都无能为力

**具体改进：**

1. `generate_exercise` 应以 LLM 输出为主，`EXERCISE_BANK` 仅做 fallback
2. `evaluate_translation` 中 LLM 产生的 `review` 只在报告末尾出现，维度评分全部来自规则引擎。应该反过来：**LLM 做初评，规则引擎做校验**
3. 增加一个 **Self-Reflection 节点**：LLM 评完后，再用另一个 prompt 复核"有没有误判？有没有遗漏？"
4. 让 LLM 直接输出结构化 JSON（维度评分 + 错误标签 + 修改建议），规则引擎只做格式校验和边界检查

### 第 2 优先：引入 RAG 做动态术语和例句检索

目前术语库是 CSV 文件 + 简单字符串匹配（`resources.py:6-12`）。评委大概率会问："遇到没见过的词怎么办？"

**建议方案：**

- 用 `chromadb` 或 `faiss` 搭建轻量向量库
- 存储内容：教材语料、真实译例、术语定义、常见错误案例
- 在 `terminology_check` 节点中，不仅做精确匹配，还做语义相似检索
- **演示亮点**：展示同一个术语在不同上下文中的不同译法；冷启动时无术语库也能给出合理建议

### 第 3 优先：从 Pipeline 升级为真正的 Multi-Agent

团队配置文档写了"Multi-Agent 协同框架"，但代码是单链路 LangGraph。建议至少引入一个**多 Agent 协作场景**。

**最小可行方案——双审校 Agent 辩论：**

```
学生译文
   ↓
Agent A (严格派)：从语法/术语角度审校 → 给出评分和问题
Agent B (宽容派)：从语义/自然度角度审校 → 给出评分和问题
   ↓
Agent C (仲裁)：比对 A 和 B 的分歧点，合成最终反馈
```

在 LangGraph 中实现方式：并行节点 + 汇总节点。演示效果极好——评委能看到不同 Agent 对同一句译文的判断分歧与最终决议。

**进阶方案——引入更多角色 Agent：**
- 术语专家 Agent：专注术语一致性检查
- 语法专家 Agent：专注格、体、搭配等语法检查
- 教学策略 Agent：根据错误类型决定反馈强度和后续训练方向

### 第 4 优先：打造可演示的差异化场景

不要试图做"全能翻译教学平台"。选 2-3 个能现场演示且打动评委的场景：

| 场景 | 演示效果 | 实现难度 |
|---|---|---|
| 小语种零资源冷启动 | 评委给一个未配置过的语言对（如中-泰），Agent 现场生成第一套练习并评估译文 | 中（依赖 LLM + 通用语言学知识） |
| 错误追踪与针对性训练 | 同一学生做 3 题，Agent 识别出"格错误"是系统性问题而非偶然失误，自动生成格专项训练 | 低（现有错题本基础上加聚类逻辑） |
| 分层提示渐进式教学 | 学生卡住 → 词汇提示 → 结构提示 → 半句提示 → 最终才给答案，全程不直接暴露参考答案 | 低（已有 hints 结构，需加强交互流程控制） |
| 翻译策略对比 | 同一原文展示直译、意译、改写三种策略的译文，解释各自适用场景 | 低（LLM 生成 + 现有框架支持） |

### 第 5 优先：准备比赛叙事

技术做得好不好占 60 分，故事讲得好不好占 40 分。建议准备一条清晰的叙事线：

> "小语种学习者面临三大困境：缺老师、缺材料、缺反馈。我们做了一个 Agent，它不是翻译器，而是一个**懂语言学、会诊断、能规划学习路径的 AI 教练**。它能在几乎没有人工标注语料的情况下，依靠大模型的语言学知识和结构化的教学框架，为学习者提供个性化训练。"

每个技术选择都应回到这个叙事：

- **为什么用 LangGraph？** —— 翻译教学需要可解释的决策链，学生需要知道"为什么扣分"
- **为什么用 Multi-Agent？** —— 翻译质量评估本身有主观性，单一模型容易误判，需要多视角交叉验证
- **为什么做分层提示？** —— 教学法要求引导而非灌输，直接给答案会破坏学习效果
- **为什么不只做翻译？** —— 翻译错误往往根源于语法、搭配、语体等底层能力，Agent 需要诊断根因而非表象

---

## 三、不要花时间的事

- **不要做繁重的语料标注**——这不是 NLP 比赛，评委关心 Agent 的智能程度而非数据规模
- **不要做复杂前端**——现有 Web UI 已经够演示用，再加功能边际收益递减
- **不要做多语种全面铺开**——把一个语言对做深（展示 Agent 的深度理解能力）远好于五个语言对做浅
- **不要把工具函数继续膨胀**——`learning.py` 已经 515 行，后续维护会成为负担。核心逻辑保留，新增能力走 LLM + prompt
- **不要过度设计评测体系**——比赛看的是 Agent 的行为和决策过程，不是 BLEU 分数

## 四、关于小语种的具体建议

如果真的想打"小语种"这张牌，建议选择一个团队有人懂、且语法/文化特征显著不同于中英文的语言作为 showcase（如：泰语、阿拉伯语、芬兰语、斯瓦希里语）。

展示点不在于语料库有多大，而在于：

1. Agent 能根据该语种的**类型学特征**（如泰语的声调、阿拉伯语的词根系统、芬兰语的格系统）自动调整评估维度和教学重点
2. Agent 在术语库为空时，仍能依靠 LLM 的语言学知识给出有效的翻译建议
3. 同一个 Agent 框架，换一套 YAML 配置就能适配一个新语种——这就是"平台"的价值
4. 演示时可以用中-俄（已有配置）展示深度，再用一个未配置的语言展示框架的扩展性

## 五、代码层面立即可做的改进

以下改进可以直接提升现有代码的竞争力和演示效果：

1. **让 LLM 输出真正参与决策**（`nodes.py:101-139`，`nodes.py:175-232`）
2. **添加 Self-Reflection/Review 节点**（在 `synthesize_feedback` 之前插入）
3. **将 EXERCISE_BANK 移到外部配置文件**，并标注每个题目的语言学特征
4. **为 `AgentRequest` 添加新字段**，支持多 Agent 辩论模式的开关
5. **添加语言对配置的 schema 验证**，确保扩展新语种时不会因配置错误而崩溃
6. **将 `learning.py` 中的硬编码错误规则移到 YAML 配置**，使框架语种无关
7. **添加 `.gitignore`**，排除 `__pycache__`、日志文件、`openai.env`、`node_modules`

## 六、团队分工建议（对应10人团队）

| 模块 | 人数 | 核心产出 |
|---|---|---|
| Multi-Agent 工作流与 LLM 集成 | 2人 | 双审校辩论、Self-Reflection、结构化 LLM 输出 |
| RAG 与知识库 | 2人 | 向量检索、术语库、例句库、RAG 与 Agent 节点集成 |
| 语言学框架与评估体系 | 2人 | 语言对配置模板、错误分类体系、评估维度设计、测试用例 |
| 交互与演示 | 2人 | Web UI 优化、演示脚本、场景演练、现场交互流程 |
| 项目统筹与文档 | 2人 | 比赛文档、演示 PPT、技术方案白皮书、答辩 Q&A 预演 |

## 总结

你们已经有了坚实的骨架（LangGraph 工作流 + 教学设计 + 工具链），现在需要的不是做更多功能，而是：

1. **把 LLM 真正驱动起来**——让它做决策而不是装饰
2. **引入多 Agent 协作**——这是比赛的核心加分项
3. **包装一个清晰的比赛叙事**——让评委记住你
4. **打磨 2-3 个可演示的惊艳场景**——比做 20 个平庸功能有效得多

5 周足够。
